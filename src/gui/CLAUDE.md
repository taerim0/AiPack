# src/gui/ — local GUI (pack + browse), Flask + pywebview

Scoped notes for `gui_server.py`, `pack_service.py`, and the static frontend (`index.html`/`app.js`/`style.css`). See the root `CLAUDE.md` for how this fits into the overall pipeline; see the `ziplex-roadmap` memory for why this exists (a local browse/search companion for environments where Claude Code/MCP isn't available but browser-based AI chat is) and what it deliberately doesn't do (autonomous web-chat querying — see that memory's "explicitly decided not to build" note).

This directory sits one level under `src/`, unlike every top-level module it imports (`query_service.py`, `file/`) — `gui_server.py`'s own docstring and its `sys.path.insert(...)` line explain why it needs to add `src/` back onto `sys.path` before those imports work when run directly (`python src/gui/gui_server.py`); `pack_service.py` needs no such bootstrap itself since whatever imports it (`gui_server.py`, or pytest via `pytest.ini`'s `pythonpath = src`) has already put `src/` on the path. Both are imported elsewhere as `from gui import gui_server` / `from gui import pack_service` — the same package-qualified style `file.*`/`extract.code.*` already use for their own cross-file imports, not a bare `import gui_server`.

## gui_server.py

The Flask app + CLI entrypoint. Two halves, split by read vs. write:

- **Read-only routes** (`/api/overview`, `/api/files`, `/api/dependents`, `/api/blast_radius`, `/api/detail`, `/api/freshness`, `/api/search`) are thin adapters over `query_service.py` — the same core `mcp_server.py` sits on — translating query params to function calls and JSON responses, nothing more. A human uses these pages to browse an already-packed project and copy what's useful (each page has a Copy button) into a separate web chat by hand; that hand-off is deliberate, not something this GUI automates (see the roadmap memory).
- **The write path** (`/api/select_files`, `/api/pack`, `/api/pack/review`, `/api/pack/link`, `/api/pack/unlink`, `/api/pack/finalize`, `/api/pack/cancel`, `/api/pack/status`) runs `packager.pack()` itself via `pack_service.py`, so a project can be packed from the GUI without a prior CLI run — see `pack_service.py` below for the actual job/review state machine these routes drive.

Runs as a local Flask server wrapped in a native window via `pywebview` by default (`main()`'s windowed branch) — `--no-window` (or a bare `flask run`/`app.run()` against the same `app` object) drops straight to a plain browser tab instead, useful for development where webview's window makes debugging fiddlier. `static_folder="."` (not `"gui"` — this file already lives in the directory `index.html`/`app.js`/`style.css` sit in) serves the frontend. Binds to `127.0.0.1` only, no `--host` flag, on purpose — the same reasoning the roadmap memory applied to rejecting a tunneled MCP server; exposing this would open local project data (including original source, via `search_project`) to the network.

**Native OS dialogs**: the windowed branch exposes a `_Api` bridge (`js_api=...`) with three methods — `choose_folder()` (project-folder fields), `choose_aif_file()` (an OPEN dialog, `.json`-filtered, for the landing page's aif.json field), and `choose_save_file()` (a SAVE dialog for the pack form's output-path field, since that target doesn't exist yet — `save_aif()` creates it). `window.pywebview.api` only exists in the native window; `--no-window`/bare-`flask run` mode has no bridge at all, so app.js's picker buttons (`hasApi()`) fall back to asking for a typed path. `_Api` is a module-level class, not nested inside `main()` (where it originally lived) — it takes the lazily-imported `webview` module as a constructor argument (`_Api(webview)`) rather than closing over a `main()`-local import, since `webview` itself deliberately stays a lazy, windowed-branch-only import (`--no-window` mode has no reason to require the package, or trigger whatever native-backend probing importing it does). Module-level also means it's directly unit-testable against a fake `webview`/window stand-in, which nesting it inside `main()` made impossible.

**Native window-close guard**: `window.events.closing` is wired to `_confirm_close_if_reviewing(window)` (also module-level, same reasoning as `_Api`), which checks `pack_service.has_reviewing_job()` and, if a job is mid-review, shows a native confirmation dialog (`window.create_confirmation_dialog`, the same mechanism pywebview's own built-in `confirm_close` option uses internally — confirmed by reading the installed package's source) that can cancel the close by returning `False`. This exists because app.js's own `beforeunload` guard (see below) only fires on an in-page reload/navigation — clicking the native window's own close button tears the webview down directly, bypassing the DOM entirely, so nothing browser-side catches it there.

## pack_service.py

Background pack-job runner backing `gui_server.py`'s `/api/pack*` routes. `packager.pack()` is long-running (real LLM calls) and talks via `print()`/`input()` — wrong to run straight inside a Flask request handler — so this runs one pack per background thread and gives the routes something to poll: a job id, a `running`/`reviewing`/`finalizing`/`done`/`error` state, captured log lines, and (once analysis finishes) a pause point for review.

- **`list_selectable_files(project_path)`** — the read-only step before a job exists: runs `collect_files()`/`scan_files()` and returns the safe/dangerous split, since `file/selector.py`'s terminal picker reads from stdin, which doesn't exist over HTTP. Whatever's checked from `safe` becomes `start_pack_job()`'s `selected_files`, which feeds `pack()`'s `preselected` param (bypassing both `auto` and the terminal picker).
- **`start_pack_job()`** runs `pack(..., interactive=False, preselected=...)` — non-interactive so a *repeated* LLM failure can't block on stdin (`checkpoint.handle_llm_failure()`'s non-interactive path) — but does **not** follow it with `finalize_aif()`. The job instead pauses in state `"reviewing"` with the raw `aif` attached, mirroring `corrector.py`'s `correct_aif()`: project name/prompt/rules, and per-file summaries triaged by `confidence.triage()` into `needs_review` (shown with real `signatures`, capped at 10) vs. `auto_kept`.
- **`add_dependency_in_job()`/`remove_dependency_in_job()`** wrap `file/relationship.py`'s `add_dependency`/`remove_dependency` — a per-edge link/unlink pair, not `move_file()`. An earlier drag-and-drop version built on `move_file()` was tried and rejected: `move_file`'s "strip from every existing reference first" step is exactly wrong for a file with more than one real parent, silently severing a shared file's other references whenever one occurrence got dragged. See `src/file/CLAUDE.md` for the pure-function side of this.
- **`submit_review()`** applies whatever the human changed through `edits.py`'s setters (the same seam `corrector.py` itself is built on), then finalizes and saves — the non-terminal equivalent of `correct_aif()`'s ending.
- **`get_review()`** recomputes `_build_review(job["aif"])` fresh on every call rather than caching it — an earlier version cached at the moment the job first paused and never invalidated it, so a page reload after a link/unlink edit could show a stale relationship graph.

**Concurrency**: each job gets its own `threading.Lock` (`job["lock"]`), acquired for every read/mutation of that job's own fields — not one global lock for every job's fields, which is what closed a real set of races caught by a two-pass code review: `get_review()`'s stale-cache bug above; `add_dependency()`'s cycle check and the actual write not being atomic (two concurrent link requests could both pass the check before either wrote, committing a cycle the guard exists to prevent); `cancel_job()`/`submit_review()` racing (a cancel arriving after `submit_review()` had already started committing could flip an already-saved job back to `error`); and a mutation dereferencing a job `cancel_job()` had just nulled out, surfacing as a raw 500. `submit_review()` moves a job out of `"reviewing"` into a transient `"finalizing"` state *before* its mutators would release `job["lock"]` — that ordering is what closes all four races together, without unrelated jobs ever contending with each other (the module-level `_jobs_lock` only guards inserting into / looking up from the `_jobs` dict itself). `has_reviewing_job()` (used by `gui_server.py`'s native-close guard) follows the same discipline: never holds `_jobs_lock` while acquiring a job's own lock. `print()`-capturing (`_capture_for_job`/`_LogWriter`) is the one deliberate exception to per-job independence — it serializes across *all* jobs via a single `_stdout_capture_lock`, since `sys.stdout` is one process-wide global no per-job lock can partition; the cost is that two jobs' analysis phases can't log concurrently, acceptable for a single-user local tool.

Jobs live in memory only (module-level `_jobs` dict) — gone on server restart, same lifetime as `gui_server.py`'s `_default_config`.

## Frontend (`index.html` / `app.js` / `style.css`)

No build step, no framework: a hand-rolled hash router (`route()`) over plain `fetch()` calls to `/api/*`. State (`aif_path`/`project_path`) lives in `localStorage`, not on the server — every `gui_server.py` route is stateless, same as `mcp_server.py`'s tools. Pages: landing (`renderLanding`), overview, files (sortable, filterable table), file detail, search, and the pack job/review flow (`renderPackJob`).

- **Relationship editor** (`renderRelationshipEditor`, inside the review flow) is master-detail, not a flat per-file list: a searchable file list on the left, and on the right only the *selected* file's own relationships — a small SVG ego-graph (`renderMiniGraph`: dependents on the left pointing in, dependencies on the right pointing out, capped at `REL_GRAPH_MAX_NEIGHBORS` (6) per side with a "+N more" overflow) plus the link/unlink controls. An earlier version rendered every file's full edge list at once with a giant unfiltered `<select>` per row to add a link — flagged directly by live user testing as unusable past a couple dozen files. Clicking a neighbor node in the graph jumps the selection to it, so a human can walk the graph instead of re-searching the file list per hop. Graph node labels show basename only (`shortLabels()`) — the full relative path was eating the fixed-width node boxes' truncation budget and clipping the actual filename — falling back to `parentDir/basename` only when two *currently displayed* neighbors' basenames collide, not project-wide.
- **Recent-projects list** (landing page, `ziplex.recent` in `localStorage`, capped at `RECENT_MAX` (8), deduped by aif path, most-recent-first) — `openProject()` is the one path that both opens a project and records it, called from the landing page's "열기" button, the pack-done screen's "결과 열기", and (indirectly, via `evaluate_js`) anywhere else a project gets opened programmatically.
- **Loading states** (`showLoading()`) on Overview/Files/file-detail fetches — factored out from the pattern `renderSearch()`'s inline "검색 중..." already used, so every page-level fetch gets a "불러오는 중..." placeholder instead of a blank `<main>` while in flight.
- **Review-screen guards**: a `confirm()` step before the "취소" button discards unsaved name/guide/rules/summary edits (relationship link/unlink edits hit the server immediately via `add_dependency_in_job`/`remove_dependency_in_job`, so those are already safe), and a `beforeunload` listener registered on entering `showReviewState()` and explicitly removed on both ways out (submit succeeds, cancel confirmed) so it doesn't linger and warn on an unrelated later navigation.

The final `aif.json` shape and the LLM-facing-function JSON contract are documented at the bottom of the root `CLAUDE.md` — nothing GUI-specific about either.
