# src/extract/ — Tree-sitter extraction & compression, plus text-only compressors

Scoped notes for `extract/code/` (Tree-sitter-based) and `extract/text/` (regex/parse-based, non-Tree-sitter). See the root `CLAUDE.md` for how these fit into the overall `pack` pipeline.

## extract/code/ — Tree-sitter (languages.py, parser.py, extractor.py, compressor.py)

- **`languages.py`** — single source of truth per language: `LANGUAGE_CONFIGS: dict[ext, LanguageConfig]`, each with `language` (the compiled Tree-sitter grammar), `function_types` (node types targeted for signature extraction + body compression), and `dependency_handler` (a `(Node, list) -> bool` callback recognizing that language's import syntax). Supporting a new extension is one `LanguageConfig` entry here — `extractor.py`/`compressor.py` never hardcode per-language node types themselves. Currently `.py`, `.java`, `.ts`, `.js` (`.js` uses the TSX grammar via `tree_sitter_typescript`).
- **`parser.py`** — `get_parser_by_ext`/`get_parser` just wrap `languages.py` to hand back a ready `Parser`.
- **`extractor.py`** — walks the parsed AST for three things, each its own traversal: `extract_signatures` (per `function_types`, builds `name(params) -> return_type` strings), `extract_dependencies` (delegates node recognition to the language's `dependency_handler`), `extract_api` (Python-specific: looks for `decorated_definition` nodes and maps `.get`/`.post`/etc. attribute calls + a string literal to `"GET /path"`-style entries — Flask-style route detection, not generalized to other languages' routing conventions).
- **`compressor.py`** — `compress_code(code, ext)` strips function bodies, replacing each with a single `MARKER` line (`"    ⋮----"`), keeping signatures/imports/decorators verbatim. Two brace-language subtleties: if the body's opening `{` sits on the same line as the signature (JS/TS/Java), the marker starts on the *next* line so the signature survives; the body's closing `}` (if present as the body's last child) is excluded from the stripped range so it isn't swallowed either. Returns `None` for an unsupported extension so callers (`compress_file()` here, and Markdown code-block compression in `extract/text/markdown.py`) can fall back to something else — both share this function for "how to compress this language," so a fix here fixes Markdown-embedded code too.

## extract/text/ — non-Tree-sitter compressors (json.py, markdown.py, txt.py, registry.py)

- **`registry.py`** — `TEXT_COMPRESSORS: dict[ext, Callable[[str], str]]`. `compress_file()` in `compressor.py` falls back here when there's no Tree-sitter grammar for the extension. To support a new text format, write a `compress_*(text) -> str` function and register it here.
- **`json.py`** — parses and keeps structure (keys), eliding only long strings (`MAX_STRING_LEN`) and long arrays (`MAX_ARRAY_ITEMS`, keeps the leading items + a marker). Falls back to returning the original text unchanged if `json.loads()` fails — never crashes on malformed JSON.
- **`markdown.py`** — line-oriented regex approximation (no Markdown AST available). Headings/blank lines always kept as structure. Lists/tables/paragraphs get the same "keep the lead, elide the rest with a marker" treatment past their own thresholds (`MAX_LIST_ITEMS`, `MAX_TABLE_ROWS`, `MAX_PARAGRAPH_LEN`). Code fences with a language tag `extract/code` recognizes (`_FENCE_LANG_TO_EXT` — kept in sync with `languages.py`'s keys) get real structural compression by calling `compress_code()` first; if the result is still long, it's truncated by line count same as everything else. Untagged/unrecognized languages skip straight to line-count truncation.
- **`txt.py`** — no structure to preserve at all beyond blank-line paragraph breaks; just the two generic rules (long block elided past `MAX_BLOCK_LINES`, long line truncated past `MAX_LINE_LEN`) that `markdown.py`/`json.py` also use for their own "body" content.
- **Circular import note**: `compressor.py` → `extract.text.registry` → `extract.text.markdown` → (for code blocks) `extract.code.compressor.compress_code` again. Both directions import the other module's function inside the function body, not at module top, specifically to break this cycle — don't "clean up" those into top-level imports.
