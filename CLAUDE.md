# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Directory-scoped detail lives in nested CLAUDE.md files, loaded automatically when you're working in that subtree — this file stays high-level on purpose:
- `src/extract/code/CLAUDE.md` — Tree-sitter code compression/extraction (`languages.py`/`parser.py`/`extractor.py`/`compressor.py`), one language per bullet (Python/Java/TypeScript/JavaScript/Lua/GDScript).
- `src/extract/text/CLAUDE.md` — the non-Tree-sitter text compressors (json/markdown/txt).
- `src/file/CLAUDE.md` — file collection, security scanning, and the dependency-graph API (`collector.py`/`scanner.py`/`selector.py`/`relationship.py`).
- `src/gui/CLAUDE.md` — the local GUI: `gui_server.py` (Flask + pywebview), `pack_service.py` (the background job/review state machine), and the frontend (`index.html`/`app.js`/`style.css`).

## What this is

Local project → `aif.json`: a token-reduced context format an AI reads instead of raw files. Pipeline: Tree-sitter compression/extraction → Gemini summarization → optional human correction. `aif.json` carries only summaries + relationships, never full per-file code — shape at the bottom of this file.

## Commands

Setup (Windows, matches the existing `venv/` in this repo):
```
venv\Scripts\activate
pip install -r requirement.txt   # note: filename has no "s"
```

Requires a `.env` with `GEMINI_API_KEY=...` (read via `python-dotenv` in `src/llm.py`).

Run any subcommand from repo root:
```
python src/cli.py pack <project_path>                              # full pipeline, interactive file selection + correction
python src/cli.py pack <project_path> --auto                       # skip interactive selection, include all safe files
python src/cli.py pack <project_path> --auto-correct                # skip interactive correction, auto-accept LLM output
python src/cli.py pack <project_path> --auto --auto-correct         # non-interactive*, for CI/scripted use
python src/cli.py pack <project_path> --no-cache                   # force-resummarize every file, ignore any previous pack
python src/cli.py pack <project_path> -o out.json                  # custom output path (also writes out.detail.json/out.cache.json)
python src/cli.py pack <project_path> --include "src/**/*.py,*.md" --ignore "**/*.generated.*"  # one-off scope, on top of .ziplex.json
python src/cli.py pack <project_path> --max-tokens 50000 --max-tokens-model GPT-4o  # CI guard: non-zero exit if the packed payload exceeds N tokens

python src/cli.py init <project_path>               # scaffold .ziplex.json (include/ignore patterns) -- see config.py
python src/cli.py collect <project_path>            # just file collection + security scan
python src/cli.py tokens <project_path>             # token count, before/after compression
python src/cli.py tree <project_path>                # dependency tree only
python src/cli.py search <project_path> <pattern> --context 2 --ignore-case  # regex search across safe files
python src/cli.py detail <name>.detail.json <file-key> --start 10 --end 40   # partial read of one file's compressed body
python src/cli.py freshness <project_path> <name>.cache.json                # hash-check aif.json against disk, no LLM calls
python src/cli.py skill <name>.json                                          # export as a Claude Agent Skill (.claude/skills/<slug>/)
python src/cli.py signatures|dependencies|api|compress|debug <single_file>
```

MCP server (exposes an already-packed project's `aif.json`/`detail.json`, read-only — see the `mcp_server.py` bullet below):
```
python src/mcp_server.py                                  # run directly, stdio transport
claude mcp add ziplex -- python src/mcp_server.py          # register with Claude Code (from repo root)
```

Local GUI (browse an already-packed project, or pack one interactively — see `src/gui/CLAUDE.md`):
```
python src/gui/gui_server.py                                            # native window (pywebview), landing page blank
python src/gui/gui_server.py --aif out.json --project ./your-project    # prefill the landing page
python src/gui/gui_server.py --no-window                                # plain browser tab instead of a pywebview window
```
*`--auto --auto-correct` makes `pack` fully non-interactive: `packager.py`'s `handle_llm_failure()` and its checkpoint-resume prompt both take an `interactive` flag now (threaded from `--auto-correct`) and skip straight to their non-interactive default — checkpoint-and-exit, and always-resume, respectively — instead of calling `input()` against a closed stdin.

Tests (`tests/`, pytest via `pytest.ini` which puts `src/` on `pythonpath`):
```
pip install -r requirement-dev.txt   # adds pytest on top of requirement.txt
pytest
```
Covers the deterministic, non-LLM logic only — compressors, extractor, `file/collector.py`'s ignore/binary filtering (including `include`/`ignore` glob scoping), `config.py`'s `.ziplex.json` load/init, `file/relationship.py`'s graph ops, `edits.py`'s pure setters, `search.py`, `freshness.py`, `confidence.py`, `skill_export.py`'s pure generation, `text_references.py`, `tech_stack.py`'s manifest parsing, `cli.py`'s `_check_max_tokens()`, and `tokenizer.py`'s counting, plus `packager.py`'s non-interactive failure handling (`handle_llm_failure`/`_resume_checkpoint_choice` with `interactive=False`, monkeypatching `input` to assert it's never called). `tests/test_pack_integration.py` runs the *full* `pack()` pipeline end to end (checkpointing, parallel summaries, rules/prompt, token counting) against `llm.MockProvider` instead of Gemini — see the `llm.py` bullet below. `tests/test_mcp_server.py` checks the MCP-specific wiring (tool registration, docstring-as-description, `call_tool` dispatch) on top of that — see the `mcp_server.py` bullet below. `tests/test_pack_service.py` covers the GUI job-runner's state machine and concurrency guards (per-job locking, the `reviewing`→`finalizing` transition, cycle/cancel/error handling) against `llm.MockProvider`; `tests/test_gui_server.py` checks the Flask route layer on top of that (status codes, error-handler mapping, request→service wiring) — see `src/gui/CLAUDE.md`. Nothing in the suite calls Gemini or needs `GEMINI_API_KEY`. `testfiles/` is separate — sample input for manual, ad-hoc CLI runs, not part of the test suite.

For a quick manual smoke test against a real project without waiting on Gemini: `LLM_PROVIDER=mock python src/cli.py pack <project_path> --auto --auto-correct` runs the whole pipeline in well under a second, network-free.

## Architecture

`src/cli.py` is a thin argparse dispatcher; all real logic lives in the modules it calls. The `pack` command runs the full pipeline end to end:

1. **`file/collector.py`** → **`file/scanner.py`** → **`file/selector.py`** — collect, security-scan, and (unless `--auto`) interactively select files. `collect_files()` takes optional `include`/`ignore` glob-pattern params (see `config.py` below) to scope collection before security scanning or selection ever run. Detail: `src/file/CLAUDE.md`.
2. **`extract/code/*`** + **`extract/text/*`** — Tree-sitter signature/dependency/API extraction and body-stripping compression for code; regex-based compression for JSON/Markdown/plain text. Detail: `src/extract/code/CLAUDE.md` / `src/extract/text/CLAUDE.md`.
3. **`tokenizer.py`** — counts tokens per model (`tiktoken`). `analyze_tokens_with_compression` (the standalone `tokens` command) measures original vs. compressed body only; `analyze_tokens_with_payload` (used by `pack`) measures original vs. just the per-file `summary` — the only per-file field that actually ships in the saved `aif.json`.
4. **`llm.py`** — Gemini REST calls (`gemini-flash-latest`, via `requests`, not the SDK) for per-file summaries, coding-rule inference, and the project-level AI guide. `LLMProvider` (a `typing.Protocol`) is the seam for adding another model — implement `generate(prompt, retry) -> str` and register it in `PROVIDERS`. Retries on HTTP 429/503 with backoff. `analyze_batch_summaries(items)` — what `pack()` calls for per-file summaries (step 5) — bundles several files' signatures/dependencies (or truncated content, for text-only files) into one prompt, one `{"summaries": {name: "..."}}` response, cutting request *count* by roughly `packager.BATCH_SIZE` (what drives 429/503 retries, not total token volume). `analyze_file_summary`/`analyze_text_summary` (single-file) still exist as the batch's per-file fallback. `PROVIDERS["mock"]` (`MockProvider`) implements that seam network-free: pattern-matches the JSON field name in a prompt's trailing example (including `"summaries"`, regexing out each batch prompt's `File: <name>` lines) and returns a fixed, valid response. Select via `LLM_PROVIDER=mock` (read once at import into module-level `_provider`) — tests instead `monkeypatch.setattr(llm, "_provider", llm.MockProvider())`, which works regardless of import order since `generate()` looks it up fresh on every call.
5. **`packager.py`** (`pack()`) — orchestrates 1–4, plus `text_references.py` for non-code files (see below), and owns **checkpointing**: `handle_llm_failure()` lets a failing LLM call be retried, answered manually, or checkpointed to `checkpoint/<project_name>.json` for the next `pack` run on the same path to auto-detect and resume. `pack(..., interactive=False)` (what `--auto-correct` sets) skips every prompt this function and the checkpoint-resume check could otherwise raise — both default to their safe non-interactive behavior (checkpoint-and-exit; always-resume) instead of calling `input()`. `pack(..., use_cache=True)` (the default; `--no-cache` turns it off) auto-detects a previous successful pack at the conventional `RESULT_DIR` path and reuses that file's `summary` for any file whose content hash still matches (via `freshness.check_freshness()`) instead of spending another LLM call on it — only `summary` is reused, `signatures`/`dependencies`/`api`/`compressed` are always freshly extracted so a human's prior manual reparenting (`corrector.py`'s `move_file()`) never silently rides along with a skipped file's stale dependency data; `relationships` is always rebuilt from scratch regardless. Pending files are grouped into `BATCH_SIZE`-sized chunks (`_chunked()`, by relative name) and submitted to the same `MAX_WORKERS` pool, one future per chunk (see `llm.py` above) — `_request_batch_summaries()` falls back to `_request_summary()` per-name for anything a batch response didn't cover, so a garbled response only costs what it actually failed on.
6. **`edits.py`** + **`file/relationship.py`** — the pure, I/O-free editing API (no `input()`/`print()`): field setters, `finalize_aif()` (builds `relationships`, prunes now-redundant `signatures`/`dependencies`/`api`), and the dependency-graph operations (`build_tree`/`move_file`/`has_cycle`). This is the seam `pack_service.py`'s GUI review flow calls directly with structured input instead of parsed terminal strings (`corrector.py` is the terminal equivalent, built on the same setters). Detail (especially `has_cycle`'s traversal direction — easy to get backwards): `src/file/CLAUDE.md`.
7. **`corrector.py`** — the thin interactive CLI wrapper around 6: walks the user through project name/guide/rules/summaries/reparenting, calling the matching pure function for each accepted change. `--auto-correct` skips this module entirely and calls `edits.finalize_aif()` directly. The per-file summary step is triaged by `confidence.triage()` (see below) -- only files below `REVIEW_THRESHOLD` get prompted; the rest are auto-kept and just listed, since reviewing every single file doesn't scale past a handful of them. Each flagged file's prompt also prints its real extracted `signatures` (capped at 10, "+N more" past that) alongside the summary, so a human can see *why* it scored low without opening the file themselves -- always non-empty for a flagged file, since one with no signatures always scores 1.0 (see `confidence.py`).
8. **`packager.py`** (`save_aif()`) — splits two things out of `aif` into sibling files: `compressed` per file → `<name>.detail.json`, so the saved `aif.json` only ever carries `summary` per file (files with little to strip, like README/config/lang files, would otherwise cost more tokens shipped than they save); and the flat `_manifest` (a `{file: content hash}` map `pack()` attaches, see `freshness.py` below) → `<name>.cache.json`, packaging-internal bookkeeping that never appears in `aif.json` itself.

**`text_references.py`** extends `relationships` past code files, for free (no LLM call, unlike Tier 3's still-open "cross-type relationship analysis" roadmap item, which this is a narrower, cheaper first slice of -- see the `ziplex-roadmap` memory). A file with no Tree-sitter grammar always got `dependencies=[]` from `extract_dependencies()`, so it only ever showed up as a leaf in `relationships` even when it obviously referenced other project files -- a Godot scene's `[ext_resource path="res://player.gd"]`, a Markdown doc mentioning `player.gd`, a README documenting a project's own layout by filename. `find_text_references_for_file(file_path, name, all_names)` (the file-level entry point; `find_text_references(content, self_name, other_names)` underneath is the pure, already-loaded-content version, used directly by tests) matches against the *actual* collected-file list (the full relative path, or just the filename+extension, both word-boundary anchored so "player.gd" doesn't match inside "multiplayer.gd") rather than a generic "looks like a path" regex -- a bare stem like "player" is deliberately never matched, since common words/stems would produce far more noise than signal, and a file with a Tree-sitter grammar is skipped entirely (its own `dependency_handler` already covers it). Because a match is already a real collected file, it needs no separate resolve step the way `extract_dependencies()`'s raw import strings do; it ends up in that file's `dependencies` list, same as a resolved import would -- **but not immediately**: `pack()` keeps text-reference matches in a side dict (`text_refs_by_path`) through the whole per-file loop and the LLM summary step, only merging them into `files_data[fp]["dependencies"]` afterward. `_request_summary()`/`analyze_batch_summaries()` both switch a file's summary prompt from content-based to signature/dependency-based the moment `dependencies` is non-empty -- merging immediately used to silently swap a text file's content-based prompt for a signatures-empty/dependencies-only one the instant it picked up any reference, so Gemini summarized it having never seen its actual text (caught by review, fixed same session; `tests/test_pack_integration.py`'s prompt-capturing regression test guards this specifically, since `llm.MockProvider` ignores prompt content and wouldn't have caught it). Wired into `pack()`'s per-file loop and, separately, into the standalone `tree` CLI subcommand -- `tree` has its own (not `pack()`-shared) collection logic, which switched from raw `collect_files()` paths to `relative_key()`-normalized keys in the process, since `resolve_dependency()`'s exact-key-match branch requires that to resolve these correctly. Known limitation, not yet addressed: a prose mention (a README) and a structural reference (a Godot scene) land in the same `dependencies` list with no way to tell them apart in `relationships`/`get_blast_radius`/`get_dependents` -- see the module's own docstring for why that's deferred rather than fixed here.

**`tech_stack.py`** — free (no LLM call), manifest-file-based fact block: `detect_tech_stack(root_path)` scans the project root's top level (not recursive) for known package-manager manifests (`package.json`/`requirements.txt`/`pyproject.toml`/`Cargo.toml`/`go.mod`/`Gemfile`/`composer.json`/`pom.xml`) and reads out each one's declared top-level dependency names (version specifiers stripped, capped at `MAX_DEPENDENCIES`, deduped). Complements `rules` rather than replacing it — `rules` is an LLM *guess* at conventions from Tree-sitter signature shape; this is a direct, deterministic read of what a manifest actually declares. `pack()` attaches its result unconditionally (`[]` if no manifest found) as `aif["project"]["tech_stack"]`, which `finalize_aif()` never touches (it only prunes per-file fields) and `skill_export.py`'s `references/overview.md` renders as an extra section when present (older `aif.json` files packed before this field existed just skip the section). Deliberately shallow: no lockfile resolution, no transitive walking — "what does this project say it depends on," not a full dependency graph.

`cli.py`'s `pack --max-tokens N [--max-tokens-model MODEL]` is a CI-guard flag, not a pipeline module: after a normal pack completes and `aif["tokens"]` is populated, `_check_max_tokens()` (pure, testable without argparse) compares the chosen model's actual packed-payload token count (the same `tokens[model]["compressed"]` figure the human-readable token summary already prints) against `N` and `main()` turns a failing/unknown-model result into a non-zero exit — for a build pipeline that wants to fail loudly if a project's context budget creeps past what a target model can hold, rather than silently shipping an oversized `aif.json`.

**`freshness.py`** sits outside the `pack` sequence like `search.py` below, but is also called *by* it (see step 5): `check_freshness(file_paths, root, manifest)` re-hashes a project's current files and diffs them against a loaded manifest into a `FreshnessReport` (`changed`/`added`/`removed`/`unchanged`, plus an `is_stale` property), with no Tree-sitter parsing and no LLM calls. Two consumers: `pack()` uses `.unchanged` to decide which files' summaries are safe to reuse (see step 5); the `freshness` CLI subcommand and the MCP server's `check_freshness` tool use the full report as a read-only "is this pack still trustworthy" check, without triggering a re-pack themselves.

**`search.py`** sits outside the `pack` sequence — pure query functions over an already-collected file set or an already-generated `detail.json`, built as MCP prep (see `ziplex-roadmap` memory: benchmarked against repomix's `grep_repomix_output`/`read_repomix_output` MCP tools before writing any MCP code). `search_files()` regex-searches original file content, not `compressed` — a match inside a body-stripped function would otherwise be invisible. `read_detail_range()` slices a `detail.json` entry's `compressed` text by 1-based line range instead of returning it whole. Exposed via the `search`/`detail` CLI subcommands, and (see below) wrapped directly by the MCP server rather than reimplemented there.

**`confidence.py`** — a free (no LLM call) heuristic for whether a summary is worth trusting: `estimate_confidence(summary, signatures)` tokenizes both (camelCase/snake_case-aware, single-suffix-"s" stemmed so "register"/"registers" count as the same word — added after a real Gemini summary scored 0.0 on nothing but that grammatical mismatch) and scores 0.0-1.0 by keyword overlap, capped at 3 matches so a file with many functions isn't penalized for a summary that abstracts over most of them. 1.0 when there are no signatures to check at all (text files) -- nothing to contradict. Called once per file in `pack()` (step 5, after summaries are final, reused or not) and stored as `confidence` alongside `summary` -- unlike `signatures`/`dependencies`/`api`, this **does** survive `finalize_aif()`'s pruning and ships in `aif.json`, since it's meant to be read by whoever consumes a summary, not just by the packing pipeline. `triage(files)` splits by `REVIEW_THRESHOLD` into (needs_review, auto_kept) for `corrector.py`'s per-file loop (step 7) and is the same function the review-scaling design leans on: not a correctness guarantee (a summary can use different words for the same idea and still be right, and this can't tell), and only as complete as `signatures` is -- a file whose real behavior lives in field initializers rather than method declarations (Java registry classes are a real example hit in testing) will score lower than it deserves, since Tree-sitter extraction only sees declared methods.

**`query_service.py`** — the transport-agnostic read-query core `mcp_server.py` and `gui_server.py` both sit on top of (same "N transports, 1 core" shape as `cli.py`/`mcp_server.py` already sharing `edits.py`/`search.py`/`freshness.py`). Holds seven functions (`get_overview`, `list_files`, `get_dependents`, `get_blast_radius`, `get_detail`, `check_freshness`, `search_project`) over `edits`/`file/relationship`/`search`/`freshness`'s existing pure functions, plus `_stale_warning()`. Read-only by design: every function reads an already-packed `aif.json`/`detail.json`/`cache.json`, or (for `search_project` and `check_freshness`) re-collects and re-security-scans the project fresh from disk on every call — none of them re-pack or re-correct a project, since that would bypass the human-correction step that's core to Ziplex's identity (see the `ziplex-roadmap` memory's "deliberately not copied" note re: repomix's per-call reconfigurable packing). `get_dependents`/`get_blast_radius` are the differentiated addition repomix doesn't have: graph queries over the *human-corrected* `relationships` tree, not just flat summary/detail lookup — `get_blast_radius` can legitimately include the queried file itself when it participates in an import cycle (verified against a real two-class mutual-import case; see `file/relationship.py`'s docstring). `get_overview`/`list_files` take an optional `project_path` -- when given, `_stale_warning()` runs the same hash-comparison `check_freshness` does (no LLM calls) and adds a `"_stale"` key only if the pack has actually drifted; omitting `project_path` skips the check entirely. Deliberately only on these two "orientation" functions -- `get_detail`/`get_dependents`/`get_blast_radius` return a bare `str`/`list[str]` with no room for a sibling field, and re-hashing on every fine-grained follow-up call would be redundant IO once the first check already surfaced drift.

**`config.py`** — an optional per-*target*-project `.ziplex.json` (not in Ziplex's own repo -- in whatever project `pack` is pointed at), analogous to repomix's `repomix.config.json` but always optional: `load_config()` never raises (missing file, bad JSON, or a non-object value all fall back to `DEFAULT_CONFIG` unchanged), so `pack()` behaves identically to before this existed with no config file at all. Scoped narrowly on purpose -- just `include`/`ignore` glob-pattern lists, the gap flagged comparing against repomix's CLI (file selection used to be all-or-nothing: everything safe via `--auto`, or one file at a time via the interactive picker, with no way to scope a pack to e.g. just `src/**` without clicking through everything else to exclude it). `pack()` loads it via `load_config(root_path)` and unions it with any `include`/`ignore` params of its own (sourced from `--include`/`--ignore` CLI flags) before calling `collect_files()` -- CLI flags augment the config file, never silently replace it. `pack_service.py`'s `list_selectable_files()` (GUI) loads the same config the same way, so the checklist a human sees in the browser can't offer a file `pack()` itself wouldn't have collected. `init_config()` (the `init` CLI subcommand) scaffolds a starter file; idempotent -- never overwrites an existing one. Living in the target project (not keyed by path inside Ziplex's own repo) means it's committable there the same way a team already commits `aif.json`/`detail.json`/`cache.json` (see README's "Team use").

**`skill_export.py`** — a third distribution channel alongside the MCP server and the GUI, for Claude Code users who haven't (or can't) register the MCP server: `export_skill(aif_path)` turns an already-corrected `aif.json` (+ its sibling `detail.json`) into a Claude Agent Skill directory (`.claude/skills/<slugified project name>/` by default — `SKILL.md` plus `references/overview.md`/`files.md`/`relationships.md`/`detail.json`), which Claude Code progressively loads on its own with no server process running at all. Inspired by repomix's `--skill-generate` (see the `ziplex-roadmap` memory), but deliberately narrower: repomix's generated `files.md` embeds every file's full raw source; this module never does — `references/files.md` stays to summaries + confidence, exactly what `aif.json` itself already restricts to, and the *compressed* (not raw) per-file body only ships as `references/detail.json`, copied verbatim from the pack's own sibling file. Shipping full source in an always-committed skill directory would undo the entire reason Ziplex compresses in the first place. Pure generation (`generate_skill_files(aif, detail)`, returns `{relative_path: content}`) is split from the I/O wrapper the same way `edits.py`/`packager.py` split, so it's directly testable without touching a filesystem. Exposed via the `skill` CLI subcommand.

**`mcp_server.py`** — the MCP server: registers `query_service`'s seven functions directly as `@mcp.tool()`s (`mcp.tool()(query_service.get_overview)`, etc.) rather than wrapping them, so each tool's docstring — what the MCP SDK reads as its description — lives in exactly one place instead of a copy kept in sync here too. Uses the official `mcp` SDK's `MCPServer` (`from mcp.server import MCPServer`; note the class was renamed from the older `FastMCP` in SDK 2.x — don't go looking for `mcp.server.fastmcp`, it no longer exists). Run with `python src/mcp_server.py` (stdio transport, the default `mcp.run()` picks).

**`src/gui/`** (`gui_server.py`, `pack_service.py`, and the static frontend) — a local GUI, positioned for environments where Claude Code (or MCP generally) isn't available but browser-based AI chat is (see the `ziplex-roadmap` memory). Read-only browse routes sit on `query_service.py` (the same core `mcp_server.py` sits on); the `/api/select_files` + `/api/pack*` family is a write path that runs `packager.pack()` itself, so a project can be packed from the GUI without a prior CLI run. Full detail (the job/review state machine, the concurrency fixes it needed, the master-detail relationship editor, native OS dialogs): `src/gui/CLAUDE.md`. Run with `python src/gui/gui_server.py [--aif PATH] [--project PATH] [--port 5321] [--no-window]`.

The final `aif.json` shape: `{ project: {name, prompt, tech_stack: [...]}, rules: [...], tokens: {...}, files: {name: {summary, confidence}}, relationships: {...} }`, with siblings `<name>.detail.json` shaped `{ file-name: {compressed}, ... }` and `<name>.cache.json` shaped `{ file-name: content-hash, ... }` (both flat, same file-name keys as `files` — not nested under a `files` key).

Every LLM-facing function in `llm.py` follows the same contract: prompt says "JSON only, nothing else," caller does `json.loads()` and falls back to a default (`{}`, `[]`, `""`) on `JSONDecodeError` — callers in `packager.py` loop until they get a non-empty result or the user intervenes via `handle_llm_failure`.
